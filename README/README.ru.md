Open-source визуальная рабочая среда для AI-кодинг-агентов. Ядро агента —
[OpenCode](https://github.com/anomalyco/opencode) (MIT); BuzzAgent — GUI-клиент
вокруг него, а не ещё один агентный рантайм.

> **Видно всё, что делает агент. Управление моделями, инструментами, браузером,
> MCP и reasoning-ом — локально, с нулевой телеметрией.**

## Почему это существует

Рынок расколот надвое:

**Визуальные, но слабые.** Cline, Kilo Code, Roo Code — UI пригодный, но
замурованный в VS Code, с телеметрией и более слабым агентным циклом.

**Мощные, но слепые.** OpenCode, Claude Code, Codex CLI, Oh My Pi — сильный
агент, но терминал. Нет визуальных диффов, нет встроенного браузера, нет
оркестрации рабочих пространств.

Брешь — это продукт, который сохраняет мощь терминального агента **и** даёт
визуальный контроль, без телеметрии и вендор-лока.

BuzzAgent — этот продукт. Он **не переизобретает агента**. OpenCode уже
является headless HTTP-сервером (`opencode serve`) со спекой OpenAPI, SSE-потоком
событий и типизированным JS SDK. Их TUI — один клиент этого сервера; их
IDE-плагины — второй. BuzzAgent — третий: самостоятельное десктоп-приложение.

CLI Kilo Code — это **форк** OpenCode, обёрнутый в расширение VS Code (линия
Cline) с аккаунтами и телеметрией. Мы это не копируем. Форк наследует их
стоимость поддержки и отрезает от апстрима. Клиент получает свежее ядро,
пока OpenCode постоянно выпускает релизы.

### У OpenCode теперь есть собственный GUI

С версии 1.18 репозиторий OpenCode публикует сборки `opencode-desktop-*`
(Electron + SolidJS, ~120–150 МБ) и браузерный режим (`opencode web`). «Визуальный
клиент для OpenCode» сам по себе **больше не дифференциатор** — у авторов ядра
он свой.

Что остаётся нашим:

- **Ноль телеметрии как проверяемый факт.** Их десктоп интегрирует
  `@sentry/solid` и инициализирует его, если при сборке задан `VITE_SENTRY_DSN`
  (`packages/desktop/src/renderer/index.tsx`), плюс `sentryVitePlugin` в сборке.
  В нашем процессе нет ни crash-репортера, ни аналитических зависимостей вообще.
- **Браузер внутри цикла агента** — пишет код, открывает результат, скриншот
  возвращается как результат инструмента, агент чинит. Не только headless: можно
  подключиться и к запущенному Chrome по CDP, чтобы агент работал в профиле, где
  пользователь уже залогинен (под разрешениями, как `shell_exec`).
- **Оркестрация worktree** — несколько агентов параллельно на изолированных
  ветках, с визуальным монитором.
- **Без аккаунта, без встроенного гейтвея.** Нет пути по умолчанию через Zen/Go.

Следствие: наш GUI будут сравнивать с их напрямую. Это поднимает планку, и
потому Milestone 1 — узкий надёжный срез, а не широкая махина фич.

Полезный прецедент из их десктопа: `packages/desktop/src/main/sidecar.ts`
запускает сервер с `OPENCODE_SERVER_PASSWORD`, случайным портом, CORS,
ограниченным собственным origin, с принудительным добавлением loopback в
`NO_PROXY` и загрузкой системных CA-сертификатов. Мы применяем то же
закаливание.

## Архитектура

```
┌─────────────────────────────────────────────────────────┐
│  BuzzAgent (Tauri + React)                              │
│                                                         │
│  Визуальный слой ──HTTP + SSE──►  opencode serve         │
│  чат · диффы · файлы ·           (бинарник sidecar,      │
│  провайдеры · разрешения ·        прибитая версия)       │
│  worktrees                                              │
│                                                         │
│  Слой Rust                                               │
│  · надзирает за процессом ядра                            │
│  · встроенный браузер (CDP) ──зарегистрирован как тул──   │
│  · оркестрация git worktrees                              │
└─────────────────────────────────────────────────────────┘
```

- **Ядро = OpenCode.** Цикл инструментов, нативный function calling, стриминг,
  сессии и возобновление, компакция, разрешения, LSP, MCP, grep/glob/symbols,
  AGENTS.md, скиллы, слэш-команды, 75+ провайдеров, OAuth. Мы ничего из этого
  не переписываем.
- **GUI = BuzzAgent.** Чат с карточками вызовов инструментов, визуальные диффы,
  дерево файлов, входящие разрешения, управление моделью/усилием по ролям,
  монитор worktree.
- **Нативные дополнения, которых нет в ядре.** Встроенный браузер в цикле
  агента; параллельные агенты в изолированных git worktree.

Фронтенд общается с ядром **напрямую** по HTTP и SSE, через `@opencode-ai/sdk`,
сгенерированный из OpenAPI-спеки **прибитой** версии (`GET /doc`). Rust не
проксирует агентный трафик. Rust только:

1. Запускает и сторожит `opencode serve` (случайный порт, пароль, health-чек).
2. Открывает нативные инструменты, которые ядро само не умеет (браузер,
   worktree).

Это тот же раздел, что OpenCode использует внутри: TUI — клиент, сервер —
рантайм.

## Почему Tauri (и чего это стоит)

Горячий путь — стриминговые токены, карточки инструментов, диффы — идёт из
вебвью прямо в локальное ядро по HTTP/SSE. Он **не проходит** через Tauri IPC,
поэтому пропускная способность IPC шелла не на критическом пути. Десктопный
шелл — решение об упаковке и нативных возможностях, а не о производительности.

Tauri, потому что:

- Нативный слой нам всё равно нужен — для надзора за процессами, управления
  браузером по CDP и git worktree; этот код написан и его тесты проходят.
- Переход на Electron ставит нас ровно на стек их десктопа (Electron +
  SolidJS + sidecar), где у авторов ядра фора и нам нечем отличиться.
- Их шаблон Electron несёт интеграцию с Sentry. Обещание «ноль телеметрии»
  проще держать правдой на стеке, который контролируем мы.
- Размер бандла здесь слабый аргумент: один бинарник ядра ~57 МБ, так что
  5 МБ против 120 МБ шелла ничего не решает.

Реальная цена, без прикрас:

- **Три разных вебвью.** WebView2 (Chromium, самообновляемый) на Windows,
  WKWebView на macOS, `webkit2gtk` на Linux. По таблице самого Tauri,
  `webkit2gtk` 2.36 ≈ Safari 16, а старые дистрибутивы ещё дальше. Linux —
  слабейшая цель, и баги рендеринга проявятся там первыми. Смягчение:
  консервативный CSS, без передовых веб-API, тесты на настоящем `webkit2gtk`.
- **Несколько вебвью в одном окне спрятаны за флагом `unstable` Tauri.** Это
  важно для панели браузера: предпочитаем CDP + скриншоты/стрим в UI, а не
  второй живой вебвью, либо отдельное окно.
- Время сборки Rust и меньшая экосистема плагинов, чем у Electron.

### Рассмотренные альтернативы

| Вариант | Вердикт |
|---|---|
| **Electron** | Самая предсказуемая UX: один Chromium везде, лучшая экосистема, простые devtools. Отклонён как дефолт, потому что это ровно стек десктопа OpenCode, а нативный код всё равно пришлось бы писать node-аддонами. Честный запасной вариант, если баги `webkit2gtk` станут неуправляемыми. |
| **Go + Wails** | Та же модель системного вебвью, что у Tauri, — та же проблема `webkit2gtk` — плюс отказ от уже написанного Rust-кода. Go здесь ничего не покупает: ядро не на Go, и наша нативная работа (CDP, worktree, надзор) на Go не проще. |
| **Чистый Rust GUI** (egui, Iced, GPUI, Dioxus native, Slint) | Устраняет весь класс багов вебвью и даёт настоящую нативную производительность. Но чат, markdown, подсветку синтаксиса, диффы и дерево файлов пришлось бы писать руками — ровно та поверхность, по которой судят GUI кодинг-агента. Крюк на годы, а панель браузера становится почти невыполнимой. Для v1 нежизнеспособно. |
| **Только веб-UI** (свой фронтенд в браузере) | Самое дешёвое, и по-настоящему полезный вторичный вариант — но OpenCode уже даёт `opencode web`, а вкладка браузера не может владеть нативными меню, worktree или встроенным браузером. Хорошо как дополнительный режим позже, не как продукт. |
| **Flutter / .NET / Qt** | Нативные виджеты, но без переиспользования React, а экосистема «markdown + диффы + код» слабее веба. Большая переписка без стратегического выигрыша. |
| **Расширение VS Code** | Знакомо и дёшево, но это коробка Cline/Kilo, против которой мы позиционируемся явно, и она убивает историю автономного приложения без телеметрии. |

Решение: **сейчас Tauri + React**, Electron — задокументированный запасной
вариант, если дефекты вебвью на Linux станут неуправляемыми. Держать UI простым
HTTP/SSE-клиентом ядра — именно это делает запасной вариант дешёвым: шелл
заменяем, потому что агентная логика в нём не живёт.

### Почему не Oh My Pi как ядро

[oh-my-pi](https://github.com/can1357/oh-my-pi) (MIT, ~30k звёзд) — сильный
агент, местами глубже OpenCode: LSP в цикле, DAP, hashline-правки, большая
нативная Rust-прослойка, URI-схемы `pr://`/`issue://`/`agent://`, цепочки
фолбэка моделей. Но *для этого продукта* это всё равно не то ядро:

- **Нет HTTP-сервера.** Его четыре поверхности — TUI, one-shot промпт,
  in-process Node SDK и `--mode rpc` / `acp` через **stdio**. Браузер не
  говорит на stdio, поэтому Rust пришлось бы проксировать каждое сообщение —
  тот слой, который мы нарочно убрали, — а их RPC требует ручной нарезки кадров
  по 1 МиБ и согласования протокола. Нет OpenAPI-спеки — нет сгенерированного
  клиента.
- **Телеметрия, которую не выключить.** Постоянный install-UUID
  (`~/.omp/install-id`, описан в их `docs/install-id.md`) переживает очистку
  состояния агента и кормит, среди прочего, отчёт об использовании auth-брокеру,
  куда уходит ещё и hostname, плюс авто-QA пуши. Убрать это — форкнуть их
  рантайм, что перечёркивает смысл чужого ядра.
- **Ниша занята:** `gooey-pi`, `pi-desktop`, `ohmypi-craft`, `ompweb` — уже
  GUI для OMP.

Если однажды добавим второе ядро — то через **ACP**, общий протокол, за
адаптерным интерфейсом, и только когда срез OpenCode станет крепким.

## Качество интерфейса — это продукт

Всё выше — сантехника. Причина выбрать BuzzAgent — интерфейс, поэтому к нему
требования стандарта, а не «работает же»: ничего не блокируется по сети, 60 fps
при стриминге, без скачков вёрстки, клавиатура вперёд, настоящие side-by-side
диффы с подсветкой синтаксиса, длинные сессии с виртуализацией, продуманные
пустые/ошибочные/офлайн-состояния, тёмная **и** светлая темы, и настоящая
доступность (фокус, контраст, поддержка скринридера для потока сообщений).

Полная планка, выбранный фронтенд-стек (React 19, Tailwind 4, Radix, Shiki,
CodeMirror 6, TanStack Virtual, cmdk) и правила добавления зависимостей — в
PLAN.md.

## Как настройка доходит до ядра

UI никогда не держит вторую копию состояния ядра. Пример — пользователь вставляет
API-ключ:

1. Панель моделей вызывает `GET /provider/auth`. Форма рендерится из схемы,
   которую вернуло ядро (API-ключ, OAuth, device flow, …).
2. При сохранении UI вызывает `PUT /auth/:id`. Ядро само пишет
   `~/.local/share/opencode/auth.json`. Ключ не лежит в нашем сторе и не в
   `localStorage`.
3. Base URL, белый список моделей, `share: "disabled"` идут через
   `PATCH /config`.
4. Пикер моделей — `GET /config/providers` / `GET /provider`.
5. Модель хода — поле в `POST /session/:id/message` (`model`, `agent`).
   «Роутер по ролям» — это наш UI, выбирающий эти поля, а не второй HTTP-клиент
   перед 75 провайдерами.

OAuth-провайдеры (Claude Pro, Copilot, GitLab Duo, DigitalOcean) используют
`POST /provider/{id}/oauth/authorize` → системный браузер →
`POST /provider/{id}/oauth/callback`. Никакого специфичного для провайдеров
кода на нашей стороне.

Если два стора снова разойдутся — агент не стартует. Ядро — единственный владелец
конфигурации, сессий, диффов и разрешений.

## Что мы делаем и чего не делаем

**Мы не пишем:** провайдеров, OAuth, цикл инструментов, стриминг, сессии,
компакцию, движок разрешений, LSP, MCP, grep/glob/symbols, AGENTS.md, слэш-команды,
скиллы, тудушки.

**Мы пишем:** весь визуальный слой; встроенный браузер как тул ядра; оркестрацию
worktree; входящие разрешения; визуальный роутер модели/усилия; надзор за
процессами; упаковку.

**Мы не форкаем OpenCode**, пока какой-нибудь вертикальный срез не докажет, что
нужно менять семантику ядра (системные промпты, поведение инструментов,
постановку диффов в стейдж). Решение принимается по доказательствам, после
Milestone 1, а не заранее.

## Позиционирование

```
BuzzAgent = ядро OpenCode
          + визуальный контроль уровня Cline
          + оркестрация worktree уровня Orca
          + встроенный браузер в цикле агента
          + ноль телеметрии
```

| | BuzzAgent | Cline / Kilo | Cursor | Claude Code | OpenCode |
|---|---|---|---|---|---|
| Open source | да | да | нет | нет | да |
| Ноль телеметрии | да (аудировано — см. ниже) | нет | нет | нет | почти (share/Zen опциональны) |
| Визуальный GUI | автономный десктоп | VS Code | да | нет | TUI / web |
| Встроенный браузер в цикле | да | нет | нет | нет | нет |
| Оркестрация worktree | да | нет | нет | нет | только сессии |
| Субагенты, LSP, MCP, разрешения | через ядро | частично | частично | да | да |
| Агностик к ядру позже | адаптерный интерфейс, OpenCode первым | нет | нет | нет | n/a |

Kilo Code доказал, что ядро OpenCode выдерживает продукт, и MIT это позволяет.
Дальше они заняли нишу IDE + телеметрия + биллинг. Ниша, которую они оставили
открытой, — ровно эта: автономный десктоп, без аккаунта, без телеметрии,
браузер + worktree.

## Ноль телеметрии — проверено

Аудит (Milestone 0) завершён и подтверждён эмпирически. Полные шаги
воспроизведения — в [docs/telemetry-audit.md](./docs/telemetry-audit.md).

- **Ноль сторонней телеметрии.** В бинарнике ядра нет Sentry, PostHog, Segment,
  Mixpanel, Datadog и никаких аналитических SDK.
- **Исходящие сетевые вызовы принудительно выключены.** Шеринг бесед
  (`"share": "disabled"`), самообновление (`"autoupdate": false`) и мелкие
  модели Zen отключены форсированным конфигом на диске.
- **Изолированная среда.** Всё состояние, кэш, база и логи изолированы внутри
  папки данных приложения (`XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_DATA_HOME`,
  `XDG_CACHE_HOME`).
- **Безопасность.** HTTP Basic со случайным 64-символьным паролем, привязка
  только к `127.0.0.1`.

## Текущее состояние

BuzzAgent пересобран и полностью работоспособен:
- **Супервизор ядра (Rust)**: автоматическое управление процессом, выделение
  случайного порта, генерация пароля, health-чеки, изоляция окружения, обход
  `NO_PROXY` для loopback, чистое завершение при выходе.
- **Прямой HTTP + SSE клиент**: прямое подключение к API ядра OpenCode, разбор
  потока событий с устойчивостью к границам кадров, управление сессиями,
  многотоходные сообщения, гейтинг разрешений.
- **Визуальный рабочий стол UI**: чат со стримингом в реальном времени без
  мерцающего markdown, блоки кода с подсветкой (Shiki), инспектируемые карточки
  инструментов с состояниями/длительностями/ошибками, диалоги разрешений.
- **Панель визуальных диффов**: просмотр git-изменений в реальном времени с
  пословными отметками (`+`/`−`) и откатом файла в один клик.
- **Панель встроенного браузера**: автоматизация headless Chrome и живое CDP
  подключение (`http://127.0.0.1:9222`), стрим скриншотов вьюпорта, взаимодействие
  через селекторы (клик, ввод), просмотр консоли CDP в реальном времени.
- **Оркестрация worktree**: создание и управление изолированными git worktree
  по веткам, мгновенное переключение активного проекта.
- **Палитра команд (`⌘K`)**: быстрая клавиатурная навигация по панелям, сессиям
  и темам (Тёмная, Светлая, Системная).

## Быстрый старт

### 1. Предпосылки и настройка

```bash
npm install
npm run setup:core   # скачать прибитый бинарник OpenCode в src-tauri/bin
```

### 2. Запуск десктоп-приложения

```bash
npm run dev          # Tauri-приложение + автоматический надзор за ядром
```

Или веб-превью:
```bash
npm run web          # только Vite — http://localhost:1420
```

### 3. Сборка установщиков (Windows / macOS / Linux)

```bash
npm run dist         # скачать прибитое ядро, затем собрать установщики релиза
```

Артефакты ложатся в `src-tauri/target/release/bundle/`:

| ОС | Файлы |
|---|---|
| Windows | `.msi`, NSIS `.exe` |
| macOS | `.app`, `.dmg` (по архитектуре: `--target aarch64-apple-darwin` / `x86_64-apple-darwin`) |
| Linux | `.deb`, `.rpm`, `.AppImage` |

Прибитое ядро OpenCode кладётся **внутрь** каждого установщика
(`bundle.externalBin`): конечный пользователь ставит один файл и никогда не
трогает терминал.

Быстрая итерация без упаковки релиза: `npm run dist:debug`.

### 4. Релиз пользователям (одна команда на все три ОС)

Установщики для всех ОС собирает CI при пуше тега версии:

```bash
git tag v0.1.0 && git push origin v0.1.0
```

GitHub Actions (`.github/workflows/release.yml`) собирает `.msi`/`.exe` для
Windows, `.dmg` для macOS (Apple Silicon + Intel) и `.deb`/`.rpm`/`.AppImage`
для Linux и прикрепляет их все к GitHub Release. Это ближайший эквивалент
`npm install -g` для десктоп-приложения: пользователь кликает одну ссылку на
странице Releases.

> Примечание: `npm install -g` — для CLI-инструментов. BuzzAgent — десктопное
> GUI-приложение; дистрибуция через установщики; глобальной установки нет.
